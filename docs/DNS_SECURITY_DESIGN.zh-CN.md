# Netch DNS 严格远程解析设计

状态：真实 IP 与验证型 Fake-IP 已实现，当前交付为 1.9.12。全进程实际验收通过；TUN 已实测，DNS/域名恢复通过但 HTTPS 超时，整体未通过。恢复边界及长期稳定性仍未完成。最终证据见 [1.9.12 记录](RELEASE_1.9.12.zh-CN.md)。设计日期：2026-09-23；状态更新：2026-09-24。改造前代码基线：197a839。

本文保留完整目标与后续设计，不能把其中所有建议视为已经交付。实际实现、验收证据和未覆盖范围以[任务总结与实施状态](DNS_IMPLEMENTATION_STATUS.zh-CN.md)为准。

## 1. 目标与术语

增加“允许本地 DNS 解析”开关，默认关闭。关闭时，Netch 管理的真实 DNS 查询只能经过指定代理出口到远程加密解析器；失败返回错误，不能自动使用系统、路由器、运营商 DNS，也不能直接连接公共 DNS。

本设计将“远程”定义为“经代理出口解析”，并非只把解析器地址改成境外 IP。本机的 DNS 监听器、缓存和 Fake-IP 映射仍可工作；它们不是向本地网络发起 DNS 查询。

本开关控制 DNS 解析路径，不保证网页访问本身全部经代理。用户已有 DIRECT 规则可以继续直连业务流量，但其域名仍通过远程 DNS 解析。若要求隐藏全部业务出口，应使用全局代理模式。

当前默认采用真实 IP 应答，Fake-IP 可选且限制模式。preview.9 完成统一映射池、域名恢复与兼容路径；preview.10 补齐回环规则与持久 TUN 路由记录，隔离回归 61 组通过。早期测试及恢复脚本失败见 [preview.9 记录](FAKEIP_PREVIEW9.zh-CN.md)；本轮两次恢复成功、全进程回环拦截问题与待复验项见 [preview.10 记录](DNS_ACCEPTANCE_PREVIEW10.zh-CN.md)。不能沿用 preview.5 的有限系统级结果宣称新版全模式通过。

## 2. 参考依据及采用范围

Clash Verge Rev 官方仓库说明其使用 Mihomo 核心。参考对象主要是 Mihomo 的 DNS 分工、Fake-IP、DNS 接管与 Windows 严格路由，而非照搬某份第三方配置。[Clash Verge Rev](https://github.com/clash-verge-rev/clash-verge-rev)

Mihomo 将应用查询、节点域名解析和直连出口解析分开配置，并支持指定 DNS 查询出口。其示例同时含有系统 DNS 和直连解析器，因此示例本身不能当成严格远程策略；尤其不能把本开关映射成 `dns.enable=false`，该设置会使用系统 DNS。[Mihomo DNS 文档](https://wiki.metacubex.one/config/dns/)

Mihomo 文档明确指出 Windows 上局域网 DNS 不能仅靠 TUN 自动劫持，并提供 `strict-route` 的防火墙保护。本项目应同时覆盖 UDP/TCP 53、局域网解析器和多网卡绕行。[Mihomo TUN 文档](https://wiki.metacubex.one/config/inbound/tun/)

Shadowrocket 的开发者产品页确认支持 DoH、DoT、DoQ，可参考其集中管理解析与代理的产品体验。未将第三方手册中未经官方确认的回退参数作为实现契约。[Shadowrocket 产品页](https://apps.apple.com/us/app/shadowrocket/id932747118)

现有 Xray 已有 FakeDNS 与域名恢复机制，因此首选保留现有代理架构，增加统一策略与保护层，不在首版同时迁移所有节点到另一个核心。Xray 的 `+local` DNS 传输会绕过正常路由，严格模式禁止用它直连外部解析器。当前实现仅使用 `tcp+local://127.0.0.1:53` 访问本程序受控监听器，随后由统一服务通过专用代理通道访问远程 DNS；此内部连接不构成本地网络解析例外。[Xray DNS](https://xtls.github.io/config/dns.html)、[Xray FakeDNS](https://xtls.github.io/config/fakedns.html)

这些来源证明参考机制的存在，不证明本项目已实现同等保护。文档中的默认值、状态机和组件划分为本项目的设计建议。

## 3. 用户界面与开关语义

设置中增加独立的“DNS 与隐私”页面，原有多个 DNS 设置不再各自决定是否允许直连。

| 项目 | 建议默认值 | 行为 |
| --- | --- | --- |
| 允许本地 DNS 解析 | 关闭 | 全局策略；关闭即强制远程，失败不回退 |
| 远程 DNS | 经过当前代理的 DoH | 主、备解析器均绑定代理；备用不是本地回退 |
| DNS 返回方式 | 真实 IP | 默认在 DNS 阶段得到远程成功或失败结果 |
| Fake-IP 增强 | 关闭，可选 | 启用时采用第 6 节的远程验证流程 |
| DNS 出口 | 当前代理链的最终出口 | 固定到具体代理路径，不受普通 DIRECT 规则改写 |
| 本地解析规则 | 无 | 仅开关开启时可编辑，规则明确指定本地解析域名 |
| 远程失败后回退本地 | 关闭 | 独立高级选项；只有允许本地解析时才能启用 |
| IPv6 | 具备完整接管能力时启用 | 否则阻断受保护范围的 IPv6 绕行，不只隐藏 AAAA |

开关关闭时，界面说明：“仅通过代理使用远程 DNS。远程解析不可用时阻止该请求并显示错误。”

开关开启只是允许本地解析：代理域名仍优先远程；匹配本地规则的域名才用本地 DNS。不得因打开开关就将全部解析改为本地。远程故障时是否允许本地回退必须由独立选项明确决定，并在状态页标为“允许本地回退”。

严格模式下旧设置 `OutboundDNS_Enabled=false`、国内 DNS 分流、单个 mode 文件、订阅更新、策略组切换都不能解除保护。冲突设置显示为“由全局 DNS 策略管理”，同时保留旧值供用户恢复兼容模式使用。

## 4. 严格模式的行为契约

1. Netch 的节点解析、延迟测试、STUN 域名、订阅与规则更新、核心内部 DNS 均接入统一策略。代理未就绪时，依赖域名的这些操作应延后或报错。
2. 查询传输优先为代理内 DoH；可选代理内 DoT。DoQ/H3 不作为首版默认，待具体核心版本与代理 UDP 能力验证后启用。不得降级成主机直连或明文直连 DNS。
3. TLS 证书必须校验。解析器若使用域名，通过代理远端解析，或用预配置连接 IP 并保留原始 SNI/证书名称；不得为解析 DoH 域名再次调用系统 DNS。
4. 主、备解析器均经过相同的受保护代理路径。网络错误或 SERVFAIL 可以切到另一个远程解析器；有效 NXDOMAIN 和有效空记录结果正常返回，不伪装成网络故障。
5. 远程解析不能成功时返回 SERVFAIL。UI 同步显示原因；不能返回随意拼出的 IP、无限等待或转为本地查询。
6. 本地 hosts、自动补全搜索后缀、mDNS、LLMNR、NetBIOS 名称解析默认不作为严格模式的隐式替代路径。localhost 与用户明确提供的节点静态 IP 作为保留用途处理；局域网发现若需要本地解析，应显式打开本地权限。
7. DNS 请求不携带用户真实网段的 ECS。日志默认记录状态、耗时、解析器及错误码，不记录完整域名历史或认证信息。
8. 允许复用未过期、来自同一远程策略的缓存；禁止混入系统/直连来源的缓存和过期应答。进入已确认的远程不可用状态后停止返回缓存，报错；恢复前先做远程健康检查。缓存命中不能被展示成“刚完成远程查询”。

DoH 的加密保护以 TLS 连接为基础；经过代理是额外的路径要求，二者都必须配置。[RFC 8484](https://www.rfc-editor.org/rfc/rfc8484.html)

## 5. 首次连接与节点域名：不保留隐藏例外

严格模式启动前，若第一跳节点只有域名且没有可信可用 IP，代理尚未建立，无法通过它完成自身解析。本设计选择报错，而不是偷偷进行一次本地解析。

允许的来源为：用户填写的节点 IP；订阅中明确提供的连接 IP；在此前正常远程会话中获得、仍在有效期内并带来源的节点 IP。静态映射与动态缓存分别标识，动态缓存不得无限延期。

使用连接 IP 时继续保留节点原始 TLS SNI、证书验证名称、HTTP Host、REALITY 等协议参数，不能简单地把所有域名字段替换为 IP。节点 IP 变化或全部失效后，停止重试并报告原因。

错误文案：“无法建立远程 DNS 通道：代理节点仅有域名，缺少可用连接 IP。本地解析已关闭。请提供节点 IP，或手动启用本地解析后重试。”

后续链式节点应通过已建立的前一跳解析/连接；若所选协议或核心无法做到，则要求为该跳提供 IP，或拒绝该配置。ECH 查询、WebSocket 主机、QUIC 端点等附属解析同样纳入依赖检查。

关闭本地解析后，订阅 URL 也不能在无代理时自动直连解析。不得通过“自动更新”“测速预解析”等辅助功能绕过这一要求。

## 6. Fake-IP 设计与失败时机

Fake-IP 的作用是维护虚拟地址与域名之间的映射，帮助透明代理按域名处理连接；它本身不证明某个远程解析器已成功解析。Xray 官方文档要求在接收连接的入站恢复 Fake-IP 对应的域名，否则连接不能正常工作。[Xray FakeDNS](https://xtls.github.io/config/fakedns.html)

为严格满足“不能远程解析就报错”，提供两种返回方式，共用同一个远程策略：

| 返回方式 | 成功条件 | 远程查询失败 |
| --- | --- | --- |
| 真实 IP，默认 | 得到有效远程 DNS 应答或有效远程缓存 | DNS 阶段返回 SERVFAIL |
| Fake-IP，经远程验证 | 先取得有效 A/AAAA 结果，再分配虚拟地址 | 不分配新的虚拟地址，返回 SERVFAIL |

第二种方式是本项目新增的前置验证要求，不应声称 Mihomo 或 Xray 原生 Fake-IP 默认如此。它牺牲部分首次查询速度，换取明确的 DNS 阶段错误反馈。不能仅打开核心 FakeDNS 就宣称完成该功能。

preview.9 实际采用：应用 DNS → 统一 DNS 服务 → 代理内远程查询成功 → Netch 托管映射池分配 → 返回虚拟 IP。为统一两种核心的生命周期并防止旧地址误用，没有直接启用核心原生 FakeDNS。

应用连接虚拟 IP 后，TUN 与 Redirector 进入 Netch 的统一 SOCKS/HTTP 入口。入口先恢复域名，再交给内部核心应用用户规则。未知映射、跨会话残留映射、冲突地址阻断并报错；虚拟地址不得发到公网或套入局域网绕过规则。当前保留游标但不保存域名历史，地址不会跨会话重新分配给另一域名；有限池耗尽后报错，尚无无限回收机制。

若连接会被送往 DIRECT，必须先通过远程 DNS 获得真实目标 IP；不得触发系统二次解析。若协议将域名交给远端代理服务器，服务端使用哪个 DNS 不完全受客户端控制，客户端只承诺不会为此发出本地 DNS 查询。

Fake-IP 只对已验证的 A/AAAA 做映射。兼容列表中的域名返回远程真实结果；进入兼容列表不意味着允许本地解析。其他记录类型（包括 HTTPS/SVCB）先通过远程原样处理，并验证后续 IP hints 连接仍受路由约束。涉及 DNSSEC 端到端校验的请求走真实应答路径；合成记录不能冒充具有真实 DNSSEC 签名的记录。

地址池在启动时检查路由冲突；切换节点/策略时按策略代际隔离缓存与映射。停止时处理系统缓存中的虚拟 IP，避免应用继续使用已失效映射。第一版 Fake-IP 仅在 TUN 或明确覆盖了全部使用该映射的进程时开放；普通选择性进程模式先使用真实 IP，避免未被接管的应用收到无法使用的虚拟地址。

## 7. Windows 上的保护范围

不能仅依赖修改网卡 DNS 或降低网卡 metric。保护分为接管、过滤、状态恢复三部分。

| 场景 | 设计 |
| --- | --- |
| 系统 DNS、UDP/TCP 53 | 重定向到受控监听器；IPv4/IPv6 同等处理 |
| 路由器/局域网 DNS、硬编码 DNS | DNS 规则优先于 LAN 绕过规则；不能重定向时阻断并报告 |
| 多网卡、Wi-Fi/有线切换 | 监听接口变化，重新应用过滤；更新期间保留阻断 |
| 进程模式的共享 DNS 服务 | 系统 DNS 统一接管，不把整个 svchost 的普通流量纳入代理 |
| DoT/DoQ | 受保护应用经代理转发，或者按策略阻断直连；不能把加密报文当明文 DNS 改写 |
| 浏览器自带 DoH | 通过其业务流量代理确保出口；仅拦截 53 无法覆盖 HTTPS 中的 DNS |
| IPv6 接管能力缺失 | 拒绝展示完整保护；阻断受保护流量的 IPv6 绕行，保留系统其他必要功能 |

必须区分两个覆盖等级：

- “系统 DNS 与选定应用受保护”：适用于进程模式。由于系统 DNS 服务共享，未选应用的系统 DNS 查询也可能被统一远程解析；未选应用自带的 DoH 不在完整保证范围。
- “全设备受保护”：要求 TUN 接管所有相关出口，并对受保护业务连接禁止不受控的直连。自带 DoH 作为 HTTPS 流量经代理转发；如保留任意应用或域名的 DIRECT 例外，界面应明确有例外，不能宣称全覆盖。

无法可靠识别任意 HTTPS/443 中的 DNS 内容，因此不以 DoH 域名黑名单作为完整保障，也不引入 TLS 中间人解密。若存在不受控的应用直连，不承诺该应用的所有加密 DNS 都经过代理。此限制需在产品中明确表达。

## 8. 生命周期与错误显示

严格保护会话的状态为：未启用 → 配置校验 → 已阻断本地解析 → 启动代理与解析服务 → 验证远程路径 → 运行中；任何运行期故障转为“远程 DNS 不可用，保护保持”。

先安装最小范围保护与恢复记录，再接管 DNS。代理/DNS 就绪前不能放行查询；核心启动日志出现 started 不等于 DNS 可用。用户规则加载和节点切换必须采用同样的保护次序。

DNS 或代理核心异常退出时，保护继续生效，不自动恢复本地 DNS。主进程崩溃时，需要持久化的最小保护规则与可恢复会话记录；单纯随进程退出而消失的过滤规则不满足该承诺。实现时验证实际 WFP/防火墙机制的崩溃行为。

“停止代理”保留 DNS 保护；另提供明确的“停止并恢复系统 DNS”操作作为保护会话终点。该操作停止接管、恢复保存的原值、清理本程序创建的规则，才结束保护。其界面状态必须显示“保护已解除”，不能仍显示“严格远程运行中”。

重启 Netch 如检测到上次未正常结束，显示“保护保持，正在恢复连接”，并提供恢复连接或解除保护入口。恢复时仅处理具有本程序标识的对象，且应避免覆盖用户在会话期间主动修改的网络设置。

| 场景 | DNS/程序行为 | 建议文案 |
| --- | --- | --- |
| 第一跳没有可用 IP | 拒绝启动连接，保持已启用保护 | 节点缺少可用 IP，本地解析已关闭 |
| 远程 DNS 超时或全部不可达 | SERVFAIL，保留阻断 | 远程 DNS 不可用，未回退本地 |
| TLS 证书无效 | 拒绝该解析器，可尝试其他受信远程解析器 | DNS 证书校验失败 |
| 有效 NXDOMAIN | 原样返回，不弹全局故障框 | 域名不存在，仅在诊断详情显示 |
| 有效无记录结果 | 原样返回，不当作超时 | 该类型无记录 |
| 监听端口冲突、过滤规则安装失败 | 不进入“已保护”状态 | DNS 保护初始化失败 |
| 未知 Fake-IP 映射 | 拒绝该连接 | DNS 映射已失效，请重新解析 |

网络故障与域名不存在必须区分。支持 EDNS 的客户端可接收适用的扩展错误；这些信息只用于诊断，不改变 DNS 返回码的含义。[RFC 8914](https://www.rfc-editor.org/rfc/rfc8914.html)

默认单次上游等待 3 秒，总查询预算 5 秒；可在预算内尝试第二个远程解析器。具体数值是本方案默认值，可配置。连续故障在 UI 聚合显示，避免每个查询弹出一个对话框。单个域名 NXDOMAIN 不使全局健康状态变红。

## 9. 落到现有代码的改造

| 组件 | 改造职责 |
| --- | --- |
| `Setting` / `SettingForm` | 增加版本化 `DnsPolicy`、开关与状态；旧字段只用于迁移和兼容配置 |
| `DnsUtils` | 所有调用转入统一解析接口；移除空参数时偷偷使用系统 DNS 的行为；按策略、记录类型、出口隔离缓存 |
| 新增 `RemoteDnsService` | 本地 TCP/UDP 监听、远程传输、有效应答缓存、错误映射、Fake-IP 前置验证 |
| 新增 `DnsProtectionController` | Windows 过滤、网卡变化、会话日志、崩溃后保护与恢复 |
| 新增 `BootstrapResolver` | 仅接收符合来源规则的节点 IP；严格模式没有系统解析分支 |
| `DNSController` / AioDNS | 严格模式不再启用旧的国内直连分支；由统一服务接管 |
| `TUNController` / `NFController` | 将 DNS 统一送入同一入口，补 TCP 53，修复 LAN 绕过优先级和共享服务遗漏 |
| Xray / sing-box 配置生成 | 明确 DNS 出口、禁止本地解析传输，恢复 Fake-IP 域名；核心不支持的能力返回明确错误 |
| `MainController` / `Guard` | 按状态机启动、停止、切换和报告故障；不以核心进程存在代替 DNS 就绪 |
| `WebUtil`、测速、订阅更新 | 全部遵守 DNS 策略；无可用通道时延迟或失败 |

建议的内部字段为 `AllowLocalResolution=false`、`AllowLocalFallback=false`、`ResponseMode=RealIp`、`RemoteResolvers`、`DnsOutbound`、`LocalDomainRules`、`BootstrapMappings`、`PolicyVersion`。不增加允许严格模式隐式例外的兼容字段。

严格模式通过独立的 DNS 路由标识绑定具体代理出口，优先级高于用户的普通 DIRECT/GeoIP 规则。新增/加载配置时检查环路、直连上游、节点依赖与旧核心能力。链式代理中 DNS 走完整代理链，节点第一跳使用明确连接 IP。

保留 Xray/sing-box 的代理职责。preview.9 采用核心前置统一映射入口，两个核心继续处理域名路由与代理连接。实际模式验收是独立阶段；隔离测试通过不代表系统驱动、网卡出口与无人干预恢复均通过。任何阶段均不得为维持联网自动降级到本地解析。

## 10. 验收与交付门槛

抓包同时观察所有活动物理网卡、虚拟网卡以及受控 DNS 服务日志。每次故障测试使用未缓存的新域名，另测缓存命中和缓存过期，避免把缓存成功误认为远程路径可用。

1. 严格模式分别测试 TUN、进程模式、全局进程模式、单节点和链式节点。系统 DNS 不出现到路由器/运营商的直连查询。
2. 测试 UDP 53、TCP 53、IPv4、IPv6、局域网 DNS、硬编码公共 DNS，以及多网卡切换。
3. 主远程解析器故障时，仅允许备用远程解析器；全部失败必须返回 SERVFAIL，物理网卡不得出现本地回退。
4. 无节点 IP 的首次启动明确失败；提供 IP 后保持原 SNI/证书验证成功；过期 IP 不得触发本地重新解析。
5. 测试浏览器安全 DNS 与应用自带 DoH；全设备保护模式下验证其连接也经代理。选择性进程模式如实报告覆盖范围。
6. 测试 NXDOMAIN、NODATA、CNAME、HTTPS/SVCB、较大 DNS 应答、TCP 分帧、DNSSEC 相关请求，确保不会误判或绕行。
7. 测试 DNS 进程退出、代理核心退出、主程序崩溃、休眠恢复、切换节点、切换开关与用户主动解除保护。
8. Fake-IP 阶段额外验证：远程失败时不产生新映射；TUN/进程入口恢复相同域名；旧映射和端口重用不串会话；停止后不残留不可用虚拟地址。
9. 加载用户现有配置，保证节点、订阅、模式文件可继续使用。测试辅助请求和更新流程不会绕过策略。
10. 校验实际生成配置与内核版本；发布可替换 `Netch.exe` 并提供 SHA-256。不能仅凭 DNS 泄露测试网页的地理位置或解析器品牌判定通过。

最终仍以只需手动替换一个 `Netch.exe` 为交付目标。主程序中的服务可以直接随 EXE 发布；必要的修复底层组件应内嵌、校验后释放到程序专用的版本目录，并显式加载，避免误用旧 `bin`。这不意味着运行时完全没有组件文件。

已使用 .NET SDK 8.0.425 构建 Windows x64 自包含单 EXE，并针对现用 `bin` 中的 Xray 26.2.6、sing-box 1.12.21 验证配置兼容性；交付继续使用原组件。构建入口为 `build-replacement.ps1`，产物、校验值及验收边界见实施状态文档。完成构建和限定环境测试不代表本节全部验收门槛均已完成。
